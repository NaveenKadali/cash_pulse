### 2.3 Cardinality Notes

- 1:1: Studio to owner User (`studio.owner_user_id`).
- 1:N: most parent-child links in the summary above.
- M:N: User (Team Member) to Project through a team-assignment join table. The join table is not yet specified and is to be defined in LLD v0.2.
- Vendor Bill to Vendor Payment is 1:N, not 1:1, because partial payments are allowed (PRD §7).
- Project stage has seven values: Booking, Vendor Setup, Shoot Completed, Digital Proofs Ready, Album Layout Approved, Print & Delivered, Financial Closed. Stage 7 (Financial Closed) is derived from financial status and is never set manually.
- Free plan limits: forecast horizon capped at 30 days; at most 3 active projects per studio (`PLAN_LIMIT`, §7).

### 4.10 Transaction Rules

- Each money write (`recordPayment`, `voidPayment`, `recordVendorPayment`, `createMilestoneSchedule`) runs in one DB transaction. The transaction writes the row, updates the derived balance, and writes an Audit Log entry.
- `createMilestoneSchedule` checks that milestone amounts sum to `contract_value` before commit.
- `voidPayment` sets `voided = true`. It never deletes the row.
- The balance read used for a decision (for example, rejecting an overpayment) is taken inside the same transaction, using `SELECT … FOR UPDATE` on the parent Milestone or Vendor Bill row.
- Client-portal calls are unauthenticated apart from the token. They may only create `Unverified` payments and never change verified ones.

## 5. Money Math (PRD §7 rules 1–10)

Conventions: all amounts are integer paise (`bigint`). Percentages are computed in integer arithmetic. Rounding is half-up to the nearest paise, applied once at the final step. No floating-point values are stored.

```
// Rule 1: Milestone balance
milestoneBalance(m) = m.amount − Σ p.amount  for p in payments(m) where p.voided = false
                                              and p.verification_status = OwnerConfirmed
// Note: Unverified payments are shown separately and do not reduce the balance.

// Rule 2: Project balance
projectBalance(proj) = Σ milestoneBalance(m)  for m in milestones(proj)
// Equals contract_value − Σ verified, non-voided payments for the project.

// Rule 3: Days overdue (Asia/Kolkata calendar day)
today = calendarDate(now, "Asia/Kolkata")          // date only, no time part
daysOverdue(m) = 0                    if m.due_date is NULL or milestoneBalance(m) = 0
               = max(0, today − m.due_date) in days otherwise

// Rule 4: Aging buckets (by daysOverdue)
bucket(d) = "0"      if d = 0
          = "1–15"   if 1 ≤ d ≤ 15
          = "16–30"  if 16 ≤ d ≤ 30
          = "31–60"  if 31 ≤ d ≤ 60
          = "61+"    if d ≥ 61

// Rule 5: Expected project contribution (no double counting)
// Each open milestone is counted once: at its actual collected amount if collected,
// otherwise at its estimate (remaining balance). Once a payment is recorded,
// the estimate for that amount is removed, so the same money is never counted twice.
expectedContribution(proj) =
      Σ collected(m)                          // actual cash from verified payments
    + Σ estimate(m)  for open m               // estimate = milestoneBalance(m), tagged SystemEstimated
    − Σ remainingPayable(b)  for bills b linked to proj
// remainingPayable(b) = b.amount − Σ vendor payments on b
// Result is shown with actual collected and outstanding costs as separate lines.

// Rule 6: Retention %
// Applies where the studio holds back part of a payment (for example, a retained share of a vendor fee).
retained = round_half_up(gross × retentionPct / 100)      // paise, integer
net      = gross − retained
// retained + net = gross exactly. Never recompute net from a rounded percentage.

// Rule 7: Daily projected balance
balance(day0) = openingBalance                            // Opening Balance Entry at as_of_date
balance(d)    = balance(d−1) + inflows(d) − outflows(d)
inflows(d)    = Σ expected milestone collections due on d        // not yet recorded
              + Σ recorded-but-not-yet-cleared, if any (none in v0.1)
outflows(d)   = Σ remainingPayable(b) with b.due_date = d
              + Σ recurring expense instances on d
// Delay overrides (what-if) move a milestone's collection to assumedCollectionDate.

// Rule 8: Shortfall
shortfall(d)  = max(0, −balance(d))
shortfallDate = min { d : balance(d) < 0 }                // first day with a deficit
// Example: balance on day 14 = −46,000 → shortfall = 46,000 on day 14.

// Rule 9: Collision attribution ("could help cover", not "will cover")
for each shortfall at date S:
  candidates = []
  a) milestones with expected collection date ≤ S and balance > 0 → add (coverPaise = balance)
  b) overdue milestones with NULL due_date and balance > 0 → add as AT-RISK (flagged, not counted
     as reliable cover unless the owner confirms a date)
  c) combinations of candidates are allowed (sum of cover values)
  d) if a candidate's expected collection date is after the vendor due date (S) → excluded
     or flagged AfterVendorDue (owner chooses in settings; default: flagged, not counted)
  coveredPaise   = min(shortfall(S), Σ counted cover)
  remainingGap   = shortfall(S) − coveredPaise           // partial coverage shows the remaining gap
// Wording in UI: "could help cover", never "will cover".

// Rule 10: Currency and rounding
currency = INR only in v0.1
storage  = integer paise (BIGINT)
display  = formatINR(paise / 100) with 2 decimals; rounding happens only at display
// Intermediate values keep full paise precision.

// FR-D-08 forecast rules (applied inside rule 7)
// (a) A recorded payment is removed from future inflows (it is no longer expected).
// (b) A recorded vendor payment reduces the remaining payable; only the remainder stays in outflows.
// (c) No double counting at the opening balance date: items dated on or before as_of_date are
//     already in openingBalance and are excluded from the forecast window.
// (d) Every forecast line is tagged OwnerConfirmed or SystemEstimated.
//     Owner-entered dates and amounts = OwnerConfirmed. Derived or assumed values = SystemEstimated.

// Final output
lowestProjectedBalance = min over d in horizon of balance(d)
lowestBalanceDate      = the date d at which that minimum first occurs
```

Plan note: forecast horizon is capped at 30 days on the Free plan (`PLAN_LIMIT`, §7). The money rules above apply unchanged to every horizon.

## 9. Transactions and Idempotency

### 9.1 Single-transaction writes

Each block below runs in exactly one DB transaction. Any failure rolls back all of its writes.

1. **recordPayment**: insert the Payment row; update the milestone status (for example, to `paid` when the balance reaches 0, or `partially_paid`); insert an Audit Log row. The milestone row is locked with `SELECT … FOR UPDATE` before the overpayment check (§4.10).
2. **Vendor payment**: insert the Vendor Payment row; update the bill's remaining-payable figure; insert an Audit Log row. The bill row is locked first. The write is rejected if the total would exceed the bill amount.
3. **voidPayment**: set `voided = true` on the Payment (never delete); reverse the milestone effect (balance and status recomputed); insert an Audit Log row.
4. **Project creation**: insert the Project row and its 3 default milestones (default 30/40/30 split, editable per PRD US-02). Milestone amounts must sum to `contract_value` before commit (§4.10).

### 9.2 Idempotency

- Required on: `POST /milestones/:id/payments` and `POST /vendor-bills/:id/payments`. Missing header → rejected (`IDEMPOTENCY_KEY_REQUIRED`).
- Stored record fields: `key`, `studio_id`, `endpoint`, `request_hash` (hash of the normalized body), `response_snapshot` (status and body), `created_at`, `expires_at`. The expiry window is set when the record is stored. Its duration is not fixed in this section.
- Lookup key: `(studio_id, endpoint, key)`.
- Same key, same endpoint, same `request_hash` → replay the stored response. No new write happens and no new audit row is written.
- Same key, different `request_hash` → conflict error (`IDEMPOTENCY_KEY_REUSED`, HTTP 409). No write happens.
- The idempotency record is written in the same transaction as the money write, so a rollback removes both.

## 10. Client-Page Rendering and Caching

- Route `/p/:token` uses dynamic SSR on every request (edge-rendered per HLD §5). It is never statically generated or cached.
- Response headers: `Cache-Control: no-store`. The HTML head includes `<meta name="robots" content="noindex">`.
- Token handling: the raw token from the URL is hashed (SHA-256) and looked up by `token_hash` (§3.14). The lookup and the status/expiry check run on every request. Nothing is cached between requests.
- Expired, revoked, or unknown token: respond with only the plain text `link no longer active`. No project data, client name, or amounts are included. The same response is used for all three cases, so a caller cannot tell which case applied. The exact HTTP status is set at implementation time.
- Active token: render only the PRD FR-G-02 fields. The page includes the client-progress-stepper (seven-stage display, HLD §11c Decided), upi-qr-image, and upi-pay-button. The payment action is production UPI only (deep link and QR, HLD §11b Decided). The sandbox gateway adapter is never shown on the client page. The client page remains read-only.

- Client-portal writes (`markIPaid`) create `Unverified` payments only (§4.7, §4.10).

## 11. Error Handling, Validation, and Logging

- Validation happens at the HTTP layer, before any service call: body shape, types, enum values, and money as integer paise. Invalid input returns `VALIDATION_FAILED` with field-level `details`.
- Domain errors (for example, overpayment, amounts not summing to contract value, bill over-payment, idempotency conflict, forbidden role) are thrown from the service layer and mapped to the one error shape `{ code, message, details }`. HTTP status mapping: validation 400; unauthenticated 401; role forbidden 403; not found 404; idempotency or state conflict 409; unexpected error 500 (generic message only).
- Logging rules:
  - Never log raw client-link tokens, token hashes, session tokens, or OTP codes.
  - Never log a full UTR. Log only the last 4 characters (masked, for example `****ABCD`).
  - Never log amounts together with client names in plain logs. Log entity IDs instead.
  - Mask client names in logs (first letter plus `***`).
- Audit Log rows (§3.15) hold the full business record and are not plain logs. They are append-only and are not exposed to Team Members.
