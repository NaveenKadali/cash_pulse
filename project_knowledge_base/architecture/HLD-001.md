**Status:** Draft v0.2

**Related:** LLD-001 (low-level design, next step). ADRs will be added under `project_knowledge_base/adr/` (see §10; not created yet).

## 1. Purpose and Scope

This document defines the high-level architecture of CashPulse, a cash-flow co-pilot for photography studios (PRD-001 §1). It covers:

- the system context and the containers that make up the web application,
- the module structure of the modular monolith,
- how each route is rendered,
- how the system is deployed in three environments with one configuration source,
- cross-cutting concerns (security, logging, backups, idempotency, time handling),
- the performance approach for NFR-03,
- the decisions still open with the user.

Detailed contracts (REST endpoints, database tables, field types, state machines, and the worked examples for the §7 calculations) are in **LLD-001**. This document does not repeat them.

**Out of scope here:** native mobile apps (PRD §13), live payment gateways (NG3; only a sandbox test-mode adapter exists, §11b), bank statement import (NG4), and photo hosting (NG5).

**External actors and systems**

- **Studio owner and team members** use the workspace (FR-J-02) on desktop or mobile.
- **End client** uses only `/p/:token` and never logs in (NG7).
- **Vendors** are not users. Their bills are recorded by the studio (§3.1).

- **Sandbox payment gateway** (Cashfree or Razorpay test mode) is evaluation-only, never used in production, and never creates a real payment (§11b).
- **UPI apps** on the client's phone receive the `upi://pay` link (FR-G-03). CashPulse only builds the link.

**Container notes**

- **Web app** renders the UI. The rendering mode per route is in §5.
- **Typed REST API** is the only way the UI reads or writes data. The UI never queries the database directly. This keeps the API the single point for RBAC (§8).
- **Domain modules** hold the business logic and own their tables. Modules call each other through their public interfaces only (§6).
- **Adapter layer** wraps the AI, SMS OTP, and payment integrations:
  - `AiServiceAdapter`: Gemini, with a deterministic template fallback for nudge and morning-brief wording.
  - `SmsOtpAdapter`: real SMS OTP in production; mock in development.
  - `PaymentAdapter`: production uses native UPI deep-link and dynamic QR only. A gateway test-mode sandbox adapter and "Simulate UPI Payment" exist only in sandbox mode. A mock also exists so the app runs with no external service.
- **Static assets and manifest** serve the PWA shell and icons (NFR-02).
- Protocols on arrows: browser ↔ app is HTTPS with JSON; app ↔ database is SQL over TLS; app ↔ providers is HTTPS. The UPI link is a URI handed to the client's device and is not a server-to-server call.

## 5. Rendering Strategy

The hybrid model follows the development rules. Each route uses the cheapest mode that meets its data needs.

| Route | Mode | Reason |
| :--- | :--- | :--- |
| `/` (public landing, FR-J-01) | **SSG / ISR** | Static marketing content, same for all visitors. ISR refreshes the "Try the live demo" entry without a full rebuild. |
| `/app`: **Cash Runway & What-If** (FR-D-01 to D-09, FR-D-07) | **SSR** for the shell and data; **CSR** widget for the what-if slider | Data is per studio and role-gated, so it must be rendered on the server for each request. The slider needs fast local recomputation of delay scenarios. |
| `/app`: **Projects & Contribution** (FR-C-01 to C-03, FR-E-01 to E-04) | **SSR** | Role-gated columns (FR-C-02). Team Members get a reduced view. |
| `/app`: **Invoices & Nudges** (FR-A-04 to A-09, FR-F-01, FR-F-04) | **SSR** for lists; **CSR** for the copy-to-clipboard message widget | Aging and balances are per studio. Copying is client-side only. |
| `/app`: **Vendor Payables** (FR-B-02 to B-07) | **SSR** | Owner-only list with due-date ordering (FR-B-05). |
| `/app`: **Settings & Team** (FR-I-01, FR-H-04, FR-H-06, FR-B-01) | **SSR** for data; **CSR** for the checklist progress widget (FR-I-04) | Team and studio data are sensitive. The checklist is interactive. |
| `/login` (FR-H-02) | **SSR** | Universal sign-in screen with two options only: "Continue with Phone" (SMS OTP) and "Continue with Email". No role-specific sign-in buttons. Workspace is resolved after login (§6, auth). Form and session creation are server-side. No caching. |
| `/p/:token` (client page, FR-G-01 to G-07) | **Edge SSR**, `noindex`, no-cache | Low latency for a phone on WhatsApp. Revocation (FR-G-07) takes effect on the next request, so the page must not be served from a cache. The UPI QR and button are generated per request. |
| `/api/*` (typed REST) | Not rendered | JSON resources. Idempotent write endpoints (§8). |

**Rules that apply to every row**

- No route renders another studio's data (NFR-11).
- No route returns a field its role may not see (§3.2). The check is on the server, not only in the UI.
- Routes that show money are not cached in shared caches.

| **invoicing** | Milestone schedule generator (30/40/30 default, flexible rules), payment recording and split across milestones, balance tracking, receivables aging, correction trail, refund as negative payment. | FR-A-02 to A-05, FR-A-07, FR-A-08, FR-A-03, FR-A-09, §7 rules 1–4, US-02, US-03, US-04 |

**Also in the repository, outside the seven modules**

- **`src/components/ui/`**: shared design-system components used by every module and route. Includes the progress stepper and the pay button, which carry NFR-10 labelling, and the plain-language tooltip for money terms (NFR-01). Modules do not import each other's UI; they compose shared primitives.
- **`src/lib/`**: infrastructure. Holds the environment configuration loader (one `.env`), database client and transaction helper, session and token utilities, the idempotency-key store, the money type (paise kept, rounding for display per §7 rule 10), the time helper (Asia/Kolkata, §8), the logger with redaction (§8), and the three adapters: `AiServiceAdapter` (Gemini plus template fallback), `SmsOtpAdapter` (with mock), and `PaymentAdapter` (UPI deep-link in production; gateway test-mode sandbox only; mock).
- **Sample data (FR-I-03)**: the seeded demo studio "Aarav Pixels" is a fixture loaded through a seed path. It is clearly labelled and removable in one action. No other fake data exists in code.

**Module rules**

- Modules expose a public interface. Other modules and routes use that interface, not internal tables.
- Money math lives only in `forecast`, `invoicing`, `vendors`, and `projects`, and is covered by tests (NFR-07). `nudges` reads figures; it never recalculates them for the record (FR-F-05).
- `client-portal` is the only module that serves unauthenticated requests. Its responses are filtered to the FR-G-02 field list.

## 7. Deployment Topology

One configuration source applies to all environments: a single `.env` file (12-factor). The same build artefact runs in each environment. Only environment values change.

| Environment | Runtime | Database (`DATABASE_URL`) | Notes |
| :--- | :--- | :--- | :--- |
| **Local dev** | Dev server on the developer machine | SQLite file, or local PostgreSQL | Mock adapters by default for AI, SMS OTP, and payments. Sandbox gateway and "Simulate UPI Payment" available only here. Aarav Pixels seed loaded on demand. |
| **Local staging** | Container built from the multi-stage Dockerfile, run locally | Local PostgreSQL | Same image as production. Used for pilot checks and the client-page path. |
| **Cloud production** | Vercel or Render, built from the multi-stage Dockerfile | Managed PostgreSQL (Neon or Supabase) | Real providers are enabled by environment values. TLS to the database. |

**Portability rules**

- Switching between SQLite, local PostgreSQL, and managed PostgreSQL requires only a change to `DATABASE_URL`. No code change.
- Switching an adapter from mock to real requires only its environment values (provider key, endpoint). No code change. The AI adapter uses `GEMINI_API_KEY`; without it, templates are used.
- Sandbox-only features are switched off by configuration in production. This is a configuration flag, not a code branch.
- Vercel versus Render is a hosting choice; both consume the same Docker image. Hosting is decided in an ADR (§10).
- Secrets come only from the environment, never from committed files.

**Build**

- Multi-stage Dockerfile: dependencies and build in one stage; a slim runtime stage with only the built output and production dependencies.
- The PWA manifest and icons are part of the static output (NFR-02).

## 8. Cross-Cutting Concerns

### 8.1 Security

- **HTTPS everywhere** (NFR-05). Plain HTTP is not served in staging or production.
- **Session cookies** carry the login session. They are set `HttpOnly`, `Secure`, and `SameSite`. Sessions expire after a period of inactivity (FR-H-06). A user can sign out of all sessions at once.
- **Server-side RBAC** is enforced on every API request and every SSR route, following §3.2 (FR-H-03). The UI hides controls for convenience only. Team Members never receive bank balance, profit, receivables, payables, forecast, or others' payout rates in any response.
- **Studio isolation** (NFR-11): every query is scoped by the caller's studio. Cache keys, exports, and logs include the studio scope. No cross-studio join is allowed.
- **Client token** (FR-G-01): random, at least 128 bits. It is stored in a form that cannot be reversed to the token. The token alone grants access; the readable name is display-only (Q-01).
- **Client page noindex** (NFR-04): responses carry a no-index directive and the page is excluded from search.
- **No-cache on `/p/:token`**: responses are not cached by the CDN, the edge, or the browser. Client-page data is excluded from analytics and caches (NFR-04).
- **Revocation** (FR-G-07): the edge checks the link status on every request. A revoked or expired link returns only "link no longer active" with no project data. Effective immediately.
- **Passwords and tokens** are stored with a one-way method, not in plain text (NFR-05). The specific algorithm is recorded in an ADR (§10).

### 8.2 Logging Rules

- Tokens, passwords, session identifiers, and OTP codes are never written to logs (NFR-05).
- Money-sensitive payloads (payment and bill bodies, amounts in request or response bodies, UTR references) are not logged. Logs record the event, the entity identifier, the user, and the outcome.
- Client-page requests are logged without the token, without the project name, and without any money value (NFR-04).
- The logger redacts known sensitive keys before writing. Redaction lives in `src/lib/`.
- Audit history is kept separately from logs. The audit trail is a data record (FR-H-05), not a log line.

### 8.3 Auditability and Corrections

- Every change to a payment, vendor payment, bill, milestone, or opening balance records user, time, old value, new value, and reason (FR-A-07, FR-H-05, NFR-06).
- Corrections and voids add history. They do not remove earlier rows (NFR-12). Refunds are recorded as negative payments with a reason (FR-A-09).

### 8.4 Backups and Recovery

- Financial records are recoverable after accidental change or deletion (NFR-12).
- Production uses managed PostgreSQL. Point-in-time recovery and retention are a platform setting. **The retention period is not decided in this document** and is to be set in LLD-001.
- Local SQLite and local PostgreSQL are for development and staging only; they hold no real studio data.

### 8.5 Idempotency and ACID Transactions

- **ACID transactions** wrap every payment-recording and invoice-changing endpoint. A payment and its milestone allocation are written in one transaction, so a balance is never half-updated (FR-A-03, FR-A-04).
- **Idempotency keys** are required on payment-recording and invoice-creation or invoice-change endpoints. A retried request with the same key returns the original result and does not create a second payment or milestone change. This matters for the double-count rule (FR-D-08) and for flaky mobile networks (A6).
- Vendor payments follow the same pattern (FR-B-07).
- The forecast reads recorded payments; it never writes them.

### 8.6 Time Handling

- All due dates, days overdue, aging buckets, and forecast day boundaries use the **Asia/Kolkata** time zone (§7 rules 3–4, 7).
- Dates are stored as calendar dates, with time-of-day kept only where an audit timestamp needs it.
- "Today" for aging and the morning brief is the Asia/Kolkata calendar date at the time of the request.
- Opening balance date (FR-D-01) is a calendar date. Transactions on or before it are not counted again (FR-D-08).

### 8.8 Product Rules Enforced in the Server

- **Sandbox-only features are disabled by configuration in production.** The gateway test-mode adapter and "Simulate UPI Payment" never run in production and never create a real payment. The client page stays read-only.
- **Free (Starter) tier limits are enforced server-side**: maximum 3 active projects and a 30-day forecast and nudge horizon. The UI may show the limit, but the API decides.
- **Stage 7 (Financial Closed)** is derived from financial status by the `projects` module. No endpoint sets it directly.

### 8.7 Money Handling

- All amounts are INR, flat, and net (§7 rule 10). Paise are kept in calculations; display rounds to the nearest rupee.
- No GST or tax field exists (NG2).
- AI output is never an input to any money value (FR-F-05).

## 9. NFR-03 Performance Approach

**Target (PRD NFR-03):** dashboard, aging, and the 90-day runway load within a couple of seconds for a studio with up to 500 projects and 5,000 payments and bills.

**How the design meets it**

- **Indexed scoping.** Every table that grows (payments, bills, milestones, alerts) is indexed on studio and on the date fields the queries filter by (due date, received date). Studio scoping (§8.1) uses the same index path, so isolation does not cost a full scan.
- **Few, shaped queries per screen.** The dashboard and aging views each issue a small set of queries that return aggregates. The forecast computes the 90-day runway in one pass over the day range rather than per day.
- **Server-side aggregation.** Balances and aging are computed on the server with the §7 rules. The client receives totals, not raw rows, so the payload stays small on a phone.
- **Parallel widgets.** The CSR widgets (what-if slider, checklist) load after the SSR shell and do not block it.
- **No AI on the path.** The morning brief uses deterministic figures; wording falls back to templates when the AI is unavailable (NFR-08). An AI call can never slow the dashboard.
- **Edge for the client page.** `/p/:token` runs at the edge for low latency. It serves one project's data, which is small.

**Verification.** How these targets are measured (test data size, method, and the threshold for pass) is part of LLD-001. This document does not claim a measured result. No benchmark has been run.

## 11. Decisions Pending

All four items below are **Decided** (PRD-001 v0.3 reflects them). The original options are kept for history. Each decision is a user decision, followed by an ADR (§10) and an update to this document.

### 11a. Authentication method: Decided

- **Decision:** One universal sign-in with two options: **"Continue with Phone"** (SMS OTP) and **"Continue with Email"**. No `[Sign in as Owner]` or `[Sign in as Member]` buttons. Every user signs in to a universal identity the same way.
- **Workspace resolution after login:** a pending studio invitation matched by phone gives the user the **Team Member** role in that studio. An existing owner goes to their **Owner** workspace. A new user completes a **30-second studio setup** and becomes **Owner on the Free (Starter) tier** (max 3 active projects, 30-day runway).
- **Rationale:** one identity model removes role-specific login paths and lets invitations work for phone-only members.
- **Original options (history):** Option 1 email only; Option 2 SMS OTP only; Option 3 both. Chosen: Option 3, with SMS OTP as a required sign-in path alongside email.

### 11b. Payment method: Decided

- **Decision:** Production uses **native UPI deep-link and dynamic QR only**. CashPulse builds the `upi://pay` link and QR. Payment is confirmed manually (FR-G-04, FR-A-03). The client page is read-only.
- **Sandbox only:** a gateway test-mode adapter (Cashfree or Razorpay test) and a **"Simulate UPI Payment"** action exist only in sandbox mode. They are disabled by configuration in production and never create a real payment.
- **Rationale:** matches the PRD's no-live-gateway scope (NG3) while still allowing realistic evaluation in sandbox.
- **Original options (history):** Option 1 UPI deep-link only; Option 2 gateway test mode as an optional adapter; Option 3 gateway live (excluded). Chosen: Option 1 for production, plus Option 2 as sandbox-only evaluation.

### 11c. Progress stage count: Decided (seven stages)

- **Decision:** Seven stages, in order: **Booking**, **Vendor Setup**, **Shoot Completed**, **Digital Proofs Ready**, **Album Layout Approved**, **Print & Delivered**, **Financial Closed**.
- **Stage 7 rule:** Financial Closed is **derived from financial status** and is never set manually.
- **Rationale:** the user's brief requires seven stages, and the stage model covers vendor setup and financial close explicitly.
- **Original options (history):** Option 1 keep six stages (PRD FR-E-01 as then written); Option 2 add a seventh stage. Chosen: Option 2.

### 11d. AI provider: Decided

- **Decision:** **Google Gemini (`gemini-1.5-flash`)** behind `AiServiceAdapter`, used for **nudge and morning-brief wording only**. A deterministic template is used when `GEMINI_API_KEY` is missing, a call fails, or a call times out.
- **Rationale:** a named provider is required for submission, and the adapter keeps it swappable. Money figures never come from AI (D-12, FR-F-05).
- **Original options (history):** Option 1 Gemini behind the adapter with template fallback; Option 2 another hosted model; Option 3 no AI in v1. Chosen: Option 1.
